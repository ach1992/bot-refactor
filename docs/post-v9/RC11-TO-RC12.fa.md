# راهنمای ارتقای RC11 به RC12

**تغییر پس از RC12:** این راهنما رفتار نسخهٔ منتشرشدهٔ RC12، شامل نرخ اختیاری نماینده را توضیح می‌دهد. طبق [تصمیم جدید مالک](https://github.com/ach1992/bot-refactor/issues/26#issuecomment-6453867569) نرخ جداگانهٔ نماینده در کاندیدای بعدی حذف می‌شود و همه از نرخ عادی استفاده می‌کنند؛ [قرارداد جدید نرخ](USDT-RATE-SETTINGS.md). فایل منتشرشدهٔ RC12 تغییر نکرده است.

[English guide](RC11-TO-RC12.md) · [معرفی پروژه](../../README.md)

این راهنما برای ارتقای نصب سازگار RC11 به [نسخهٔ منتشرشدهٔ RC12](https://github.com/ach1992/bot-refactor/releases/tag/v0.10.0-rc.12) است. کل بستهٔ runtime و manifest معتبر همان انتشار را دریافت کنید. انتشار سورس به معنی نصب روی ربات یا تأیید عملیاتی نیست. راهنماهای پیوست انتشار، تصویر ثابت سورس بررسی‌شده‌اند؛ این راهنمای جاری وضعیت انتشار را نیز منعکس می‌کند.
RC11 منتشرشده و شواهد تاریخی آن تغییر نمی‌کنند. نصب، SQL، وبهوک، Cron و
عملیات واقعی مالی/پنل مجوز جداگانه می‌خواهند؛
[دروازه‌های Issue #81](https://github.com/ach1992/bot-refactor/issues/81)
برقرارند. نصب RC9 باید [مسیر RC9 به RC11](RC9-TO-RC11.md) را دنبال کند.

## آماده‌سازی بسته و پایگاه داده

1. ربات، نسخه، پایگاه داده، فاکتورهای باز، عملیات نامشخص و زمان‌بندی‌ها را
   شناسایی کنید. از فایل‌ها/تنظیمات/داده‌ها پشتیبان خصوصی بگیرید و بازیابی را
   در محیط جداگانه تمرین کنید. نصب‌های دیگر را تغییر ندهید.
2. **کل بستهٔ runtime** و manifest معتبر همان نسخه را بررسی کنید؛ آرشیو
   خودکار Source code گیت‌هاب جایگزین runtime تأییدشده نیست. بستهٔ RC12
   **112 فایل runtime** دارد؛ `messages/loader.php` و هر دو فایل
   `messages/fa/user.php` و `messages/fa/admin.php` لازم‌اند. کپی چند فایل
   تغییریافته یا حذف `messages/` نصب کامل نیست.
   [روش بررسی بسته](RC11-TO-RC12.md#inventory-schema-and-source-preparation) و
   [بررسی فقط‌خواندنی readiness](PAYMENT-READINESS-PREFLIGHT.md) را بخوانید.
   تطبیق با manifest نامعتبر، اصالت بسته را اثبات نمی‌کند.
3. ساختار واقعی و دفترهای مالی RC11 را بررسی کنید؛ استخراج ZIP هیچ SQL یا
   پاک‌سازی اجرا نمی‌کند. فقط تغییر غایب و بررسی‌شده، با مجوز جداگانه،
   قابل اعمال است؛ جدول موجود را دوباره نسازید.
4. پس از راه‌اندازی آزمایشیِ مجاز، تنظیمات نمایش و نرخ‌ها را در رابط مدیر
   تعیین کنید؛ سپس مسیرهای مربوط را بیازمایید. این کار مجوز پرداخت واقعی،
   ایجاد حساب واقعی یا اجرای بی‌برنامهٔ Cron مالی نیست.

| بخش | قاعدهٔ ارتقا از RC11 سازگار |
| --- | --- |
| دفترهای موجود، به‌ویژه `wallet_adjustments` | داده، هر دو سمت انتقال و سابقهٔ ضدتکرار حفظ شود؛ **005 را دوباره اجرا نکنید، RC10 را وارد یا تغییرنام ندهید.** ناسازگاری بررسی جداگانه می‌خواهد. |
| [011_provider_identity.sql](../../migrations/post-v9/011_provider_identity.sql) | افزایشی و جداگانه؛ **فقط برای PasarGuard لازم است**. نصب صرفاً Marzban به آن نیاز ندارد. وضعیت ناقص/ناسازگار باید بررسی شود؛ اجرای مجدد کورکورانه راه ترمیم نیست. |
| [ابزار و manifest پاک‌سازی 010](CURRENT-RUNTIME-CLEANUP.md) | اختیاری و مستقل از ارتقا/011؛ **DROP خودکار نیست**. ابزار پیش‌فرض فقط بررسی می‌کند. اعمال آن مجوز نگهداری جداگانه، شکل دقیقِ خالی، بررسی وابستگی و تعیین تکلیف نگهداری می‌خواهد؛ داده/شکل ناشناخته حفظ می‌شود. |

## تنظیمات خصوصی، نمایش و نرخ‌ها

**فایل واقعی `baseInfo.php` را حفظ کنید.** بسته آن را شامل نمی‌شود و این
تغییر مقادیر قدیمی را خودکار وارد یا حذف نمی‌کند. شش متغیر زیر دیگر منبع
تنظیم runtime نیستند؛ حذف آن‌ها از مثال عمومی، فایل خصوصی را تغییر نمی‌دهد:

`hideConnectLinkForMarzban`، `showIndexes`، `hideConfigIfMany`، `linkIndices`،
`USDTPrice` و `USDTPriceagent`.

در **تنظیمات هر سرور منطقی → نمایش لینک و QR**، نمایش کانفیگ/اشتراک، QR،
محدودیت‌ها و انتخاب هدایت‌شدهٔ پروتکل/نام را تعیین کنید. سرورهای مشترک روی یک
پنل هم تنظیم مستقل دارند. انتخاب شماره‌ای Marzban باید صریحاً در حالت
مدیریت‌شده تنظیم شود؛ PasarGuard از آن شماره‌ها استفاده نمی‌کند.
نبود تنظیم از پیش‌فرض مستند native استفاده می‌کند؛ انتخاب قدیمی خودکار وارد
نمی‌شود. تنظیم نامعتبر/تکراری خروجی را محدود می‌کند.
[جزئیات نمایش اشتراک](SUBSCRIPTION-PRESENTATION.md).

در **تنظیمات درگاه ربات**، پیش از پرداخت جدید نرخ‌ها را تعیین کنید:

| کلید | کاربرد |
| --- | --- |
| `manualUsdtRateToman` | نرخ عادی هر USDT به تومان، مشترک برای USDT دستی و تبدیل NOWPayments. |
| `usdtAgentRateToman` | نرخ اختیاری نماینده؛ نبود مقدار یا `/clear` از نرخ عادیِ صریح استفاده می‌کند. مقدار صریح نامعتبر فقط نرخ نماینده را غیرقابل استفاده می‌کند. |
| `manualTrxRateToman` | نرخ مستقل TRX؛ از USDT یا متغیرهای قدیمی استنتاج نمی‌شود. |

بدون نرخ معتبر، گزینهٔ مربوط برای همان گروه در دسترس نیست؛ نرخ مستقل معتبر
نماینده می‌تواند با نبود نرخ عادی همچنان قابل استفاده باشد. نرخ خصوصی،
دریافت خودکار قیمت و پیش‌فرض 1:1 وجود ندارد. فاکتور ثبت‌شده پس از تغییر نرخ،
مبلغ/شبکه/مقصد/نرخ اصلی را حفظ می‌کند. رمزارز دستی همچنان بررسی انسانی می‌خواهد.
[قرارداد نرخ‌ها](USDT-RATE-SETTINGS.md).

## PasarGuard و متن‌های ربات

سورس برای **PasarGuard 5.5.1** و Marzban مسیر مستقل دارد. برای PasarGuard،
011 سازگار، Groupها/Hostهای native معتبر و پیشوند کامل و مطلق URL اشتراک
پیش از استفاده لازم‌اند. کلید API باید مجوز محدود لازم برای کاربران و
خواندن Groupها و محدودهٔ مجاز Group را داشته باشد؛ نام دقیق مجوزها و
الزامات RBAC در [قرارداد PasarGuard](PASARGUARD-CONTRACT.md) آمده است.
Group پنل با گروه مشتریان پرداخت یا گروه فیزیکی Marzban یکی نیست.
User Template، `on_hold` و زمان‌بندی native برنامهٔ بعدی/بازنشانی مدیریت
نمی‌شوند. پاسخ نامشخص CREATE یا ویرایش مجوز ارسال دوباره نیست.

متن‌های ربات و صفحه‌های PHP پرداخت فقط از 2 فایل ویرایش می‌شوند:
`messages/fa/user.php` برای مشتری/همکار و برچسب‌های مشترکِ امن، و
`messages/fa/admin.php` برای مدیریت و پیام‌های مخصوص ادمین. داخل هر فایل
بخش‌بندی موضوعی وجود دارد. loader و settings/values.php فقط کد/رابط سازگاری‌اند.
ارقام متن‌های خود ربات ASCII هستند. اموجی مرتبط در شروع پیام کامل، بدون
اموجی‌های انباشته، و قالب بولد/کد فقط در محل پشتیبانی‌شده استفاده می‌شود؛
اجزای تاریخ، واحد و ادامهٔ جمله را مثل پیام کامل تغییر ندهید.
[نقشهٔ ویرایش پیام‌ها](RC11-TO-RC12.md#message-editing-map) و
[قرارداد کاتالوگ](../../messages/README.md) فایل مناسب را نشان می‌دهند.
کلید پایدار، پارامترها، placeholderهای قدیمی و HTML/escaping را حفظ کنید؛
callback، وضعیت ذخیره‌شده، SQL، فیلد پنل و کد تشخیصی را ترجمه نکنید.
ویرایش متن هویت سورس را عوض می‌کند و بررسی و بستهٔ متناظر می‌خواهد.

## فاکتورهای قدیمی و بازگشت امن

فاکتور جدید حجم/روز، تعداد **صحیح GiB/روز** و قیمت اصلی را در فیلدهای موجود
`pays.volume` یا `pays.day` و `pays.price` نگه می‌دارد؛ محور دیگر صفر است.
تغییر یا حذف SKU مقدار فاکتور صادرشده را عوض نمی‌کند. تعداد قدیمیِ صفر،
NULL، غایب یا ناسازگار، استحقاق اصلی را اثبات نمی‌کند: ادعای جدید، برداشت
کیف پول و اثر پنل از آن مجاز نیست؛ رکورد قبلاً پرداخت/رزرو/درحال‌پردازش‌شده
برای بررسی نگه داشته می‌شود. **با مقدار امروزِ کاتالوگ پر نکنید؛ عملیات،
بازپرداخت یا اصلاح خودکار انجام ندهید.** شواهد اصلی پرداخت/فاکتور/پنل باید
تطبیق داده شوند. [مرز مالی افزونه‌ها](FINANCIAL-CONSOLIDATION.md#immutable-add-on-quantity-and-rc11-pending-invoice-boundary).

خانه، فاکتور/وضعیت/مدرک را حفظ می‌کند و منوی تازه می‌فرستد. فهرست رسیدگی
اثبات تحویل همهٔ پرداخت‌ها نیست. کنترل‌های افزایش/کاهش کیف پول باقی‌اند؛
کاهشِ ایجادکننده یا افزایندهٔ بدهی، پیش‌نمایش و تأیید صریح جداگانه می‌خواهد.
پیام مشتری/مدیر از نتیجهٔ ثبت‌شده می‌آید؛ خرابی پیام پول را برنمی‌گرداند.
[قرارداد کیف پول](ADMIN-WALLET-ADJUSTMENTS.md) و [دامنهٔ نسخه](NEXT-RELEASE.md).

برای rollback، سورس و زمان‌بندی را کامل و هماهنگ برگردانید؛ worker قدیمی و
جدید همزمان اجرا نشوند. **مانده‌ها، دفترهای مالی/اثر/ضدتکرار، cursorها،
هویت پنل/حساب و حساب‌های واقعی را حفظ کنید.** قدیمی‌کردن سورس تراکنش را
خنثی نمی‌کند. 011 یا دفترها را حذف نکنید، سابقهٔ ضدتکرار را پاک نکنید و
پایگاه دادهٔ قدیمی را کورکورانه برنگردانید؛ پول‌های بعد از پشتیبان ممکن است
از بین بروند و عملیات تکرار شود. نسخه‌ای که وضعیت PasarGuard یا دادهٔ مالی
جدید را نمی‌فهمد نباید همان رکوردها را پردازش کند. بازیابی/ترمیم به برنامهٔ
جداگانه و تطبیق آثار نیاز دارد؛ این راهنما تأیید عملیاتی یا مجوز نصب نیست.
