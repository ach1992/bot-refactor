## Current post-V9 supported-product contract — Owner-confirmed 2026-10-14

**Authoritative contract:** [Issue #31](https://github.com/ach1992/bot-refactor/issues/31) owns the post-V9 Marzban-only acceptance, and [Issue #29](https://github.com/ach1992/bot-refactor/issues/29) defines the remaining roadmap. The intentionally changed post-V9 implementation is integrated into `main` by [PR #32](https://github.com/ach1992/bot-refactor/pull/32); the frozen published V9 source and its historical evidence remain separate. **Source integration, public release, installed behavior, real MariaDB migration and operator approval are different gates.** The current post-V9 contract must never be misrepresented as a completed production rollout.

**Purpose:** retain the desired bot, user/admin/agent, purchase/renewal, support, reporting, scheduled and wallet functions with less coupling and obsolete code, while **keeping the original 23-table MariaDB schema and persisted data unchanged by default**. Broad schema redesign/new features/performance reengineering belong to a later independently accepted phase.

**Customer-facing error contract — Owner-confirmed 2026-10-16:** tell customers what they can safely do (retry only when idempotent, check status, or contact support) without revealing internal VPN panel/provider names, SQL/database/API infrastructure, raw exception strings or internal status codes. Give authorized operators more precise **private**, redacted reason codes, a correlatable request/payment reference, and enough bounded context to diagnose or reconcile the issue. Technical terminology remains valid in admin configuration/diagnostics, not ordinary end-user service/payment failures. A failed notification or ambiguous external operation is never proof a committed financial effect was rolled back. Telegram failure/rate-limit logs must omit raw message payloads, private operator notices, provider response snippets and potentially secret-bearing transport errors; keep only safe diagnostic metadata. Existing installed logs containing old raw entries require separate access-controlled inspection/rotation, never a repository-level assumption of cleanup.

**Supported VPN backend now: Marzban only.** The Owner explicitly confirms that **legacy X-UI, Sanaei, Alireza, old 'normal' panel variants have NEVER been operated**, and authorizes **fully removing** their networking, management/wizard, configuration/link-building and dead branches from the next source iteration. **No backups, data export, migration or cutover for these nonexistent legacy panel deployments are required.** This narrow old-panel waiver never waives actual bot/customer/Marzban/financial data backup, schema migration, or restoration safety. Never infer that an unexpected legacy server record should use Marzban: reject unknown/retired types before provisioning/charging/deletion with safe feedback. No real provider state or real DB is to be modified as part of source refactoring.

**Owner-confirmed logical Marzban server switching — R4 (2026-10-15):** multiple logical bot servers may refer to the same physical Marzban account store even if their **API endpoint URLs or admin usernames are different**. Only a valid, explicit admin-assigned *shared panel group* proves same-panel identity; never infer it from URLs, credentials, display flags or forged/stale callbacks. Administrators define named panel groups in the server-management UI, select an existing group during onboarding or later editing, and may leave a server **unassigned** (then switching is disabled). Group definitions use normal rows of existing `setting` with `type='ACHBOT_MARZBAN_PANEL_GROUP'`; `server_info.panel_group_id` is a **single new nullable column** referencing that definition by its numeric ID. Existing server rows remain unassigned after upgrade until an admin explicitly groups them; group edits that would strand already switched plan-linked orders must fail closed. Switching within a shared group changes **ONLY `orders_list.server_id`**, keeping the remote Marzban account/proxy/inbounds/protocol, token, UUID, link, original plan/fileid/pricing, wallet and capacity untouched. Distinct product plans and prices on logical servers remain independently configurable. Cross-panel actual migration, automatic real Marzban/PasarGuard config reconciliation, other provider adapters and financial redesign are future independently authorized work. See [superseding Owner decision](https://github.com/ach1992/bot-refactor/issues/31#issuecomment-6184330243).

**Current schema exception, not retroactive V9 parity:** Owner approved the **additive, nullable** `server_info.panel_group_id` column ONLY for the new post-V9 increment. The historical `database/legacy-schema.sql` and pinned V0–V9 test/golden archives stay byte-frozen with their **original 23 tables and columns**. The new current runtime expects the same 23 tables **plus this one column**, installed separately using `migrations/post-v9/001_marzban_panel_group_id.sql`. No existing server/group memberships are auto-backfilled. Real tenant migration/deployment requires separate explicit Owner authorization, backup/restore proof, staged rehearsal and verification per `docs/post-v9/PANEL-GROUPS-MIGRATION.md`; a source-only rollback can retain the harmless extra nullable column. No real database changes were authorized by source implementation.

**Extensibility:** keep a *minimal* explicit provider boundary for Marzban account create/read/update/delete, renewals, links, status and traffic. **PasarGuard, next-generation X-UI and other unknown panels are future optional implementations, NOT current supported transports.** Do not build speculative APIs or compatibility flags for panels that have not yet been selected.

**Wallet:** `users.wallet` may be negative to reflect **explicit debt set by a privileged administrator**. Ordinary users must **never** create or deepen debt via wallet spend, transfer or renewal. A distinct auditable administrator-debt operation is required; never globally enforce wallet >= 0. This is a **desired future policy** tracked under [#26](https://github.com/ach1992/bot-refactor/issues/26), not retroactive financial safety certification of published V9.

**Financial core — Owner-approved direction 2026-10-16 (Issue #26):** consolidate existing and future payment gateways behind provider-specific initiation/verification adapters and **one authenticated, idempotent local payment/fulfillment lifecycle**. The shared core must protect original merchant order identity, provider-scoped attempt identity, amount/units, concurrency, replay, durable business effects and recovery from external Marzban/Telegram partial failure. Browser redirects and hosted checkout success screens are NOT payment proof; only a verified provider response can authorize financial completion. Keep receipt/admin/wallet routes logically distinct but subject to shared effect and audit invariants; retain the privileged negative-wallet debt policy above. For NOWPayments the accepted server-verified final status is **`finished`**; `confirmed` and `sending` are intermediate and must not grant service/credit. The inherited automated TRON checker is retired from active execution due to its unsafe legacy success check, missing historical amount field and TLS gaps. Prefer existing MariaDB schema during characterization, permit only evidenced **additive**, backward-compatible financial persistence with separate Owner migration/backup/rollout approval; **never redesign or drop original 23 historical tables by default**. Keep public callbacks/Cron entrypoints stable, preserve historical V0–V9 source/goldens, and prohibit live payments/provider/balance/SQL side effects during repository development. Specialized implementation, status mapping, rollout gates and remaining decisions: [Financial Consolidation](post-v9/FINANCIAL-CONSOLIDATION.md) and [Issue #26](https://github.com/ach1992/bot-refactor/issues/26).

NextPay likewise has no old transactions to migrate but remains an OPTIONAL supported gateway for new provider-neutral payments. Manual TRX/TRON, USDT/TRC20 and NOWPayments are distinct supported flows. Keep immutable V0–V9 source/history, published releases and actual installed financial data untouched. A future separately authorized deployment must remove only the retired package members while protecting private config, supported runtime and rollback, not blindly extract a ZIP over stale PHP. **Manual-payment architecture — superseding Owner decision 2026-10-18 (Issues #51 and #26):** Keep bank transfer (`cartToCartState`) and gift cards (`giftCardState`) as independent manually reviewed methods, plus a **single manual crypto method selection** under existing `manualUsdtState`. Its four independently configured destinations are **USDT BEP20** (`manualUsdtWalletBEP20`), **USDT TRC20** (`manualUsdtWalletTRC20`), **USDT ERC20** (`manualUsdtWalletERC20`), and **native TRX TRON** (`manualTrxWallet`). USDT and hosted NOWPayments conversion require the explicit normal `PAYMENT_KEYS.manualUsdtRateToman` rate, with optional `usdtAgentRateToman` for actual agent accounts. Missing/cleared agent override uses the explicit normal rate; invalid explicit override disables only agent USDT quoting. No private/external/1:1 rate fallback exists; native TRX **requires** independent `manualTrxRateToman`, never the retired chain-checker rate. Each missing/invalid address or rate hides **only that option**; /clear disables a configured address or rate. Preserve old single-network USDT settings for compatible already configured instances; **never** silently enable manual TRX from old `tronwallet`. One selection menu covers purchases, renewals, extensions, and wallet top-ups, but each existing payment subject retains its own guarded receipt/admin effects.

A protected one-attempt claim in `payment_attempts` persists original provider `manual_usdt` or `manual_trx`, asset, chosen network, destination, Toman conversion rate and **rounded-up** quoted amount. A future setting edit may not rewrite an already claimed invoice. The screenshot is untrusted evidence: only independent administrator verification followed by the existing protected approval may credit a wallet or deliver a service. Old automatic TRON checker/TXID input callbacks and its Cron worker are retired, fail closed and do not change historical balances or evidence. Source development and isolated tests do not approve release, migration or production use.

**Future extension only (not implemented):** the provider-scoped attempt/transaction ledger and separated evidence/fulfillment boundary permit a *new* independently reviewed, authorized on-chain verifier (correct token contract, recipient, amount, chain, confirmations, settled finality, durable replay protection), without trusting screenshots or reviving old TRON code. Automated crypto settlement is **OFF**, not implicitly scheduled.

## Historical Phase 1 V0–V9 contract — completed source integration, original reference only

The following sections describe the **immutable, historically accepted behavior-preserving** source-refactor phase, not a rule that prevents the Owner's later explicitly authorized Marzban-only removal. Their test sources and released evidence must remain truthful and independently reproducible.


## Outcome

Incrementally refactor the existing PHP Telegram VPN bot so the final operator can replace the bot application source on its existing deployment without changing its existing MariaDB database, business rules or user-visible/admin-visible behavior. Improving readability, maintainability, testability and future extension is the purpose of the change.

## Non-negotiable compatibility

1. **Database:** No DDL, migration, table/index/column changes, writes for repair/migration, or data re-encoding as part of Phase 1. Ordinary application data writes must continue with equivalent semantics.
2. **Observed behavior:** Maintain commands, menus, labels, callback handlers (including in-flight legacy callback strings), state transitions, price/calculation rules, purchase, extension, renewal, discounts, wallet accounting, bot/admin/agent permissions and notification behavior.
3. **Integrations:** Maintain Telegram webhook entrypoint, return URLs, active subscription endpoints, remote VPN panel adapters, gateway/payment return behavior, Cron file paths and timing assumptions until replacements are proven compatible.
4. **Operator experience:** Every refactor increment must be complete and independently deployable with a documented file swap, readiness checks, human-tested acceptance and rollback.
5. **`baseInfo.php`:** Keep actual local file and values untouched. Do not attempt a breaking config migration. Consider any structural change only in the last increment.
6. **Bugs:** Changes that might alter external behavior are separately scoped, evidence-backed, testable and explicitly accepted; when uncertain, preserve old behavior behind a seam for later repair.
7. **Phase 2:** Future schema migration is outside Phase 1. Add application boundaries allowing future storage refactoring; do not over-engineer abstractions.

## Acceptance gates per increment

- Recorded initial baseline, integration/entrypoint inventory and explicit scenario-by-scenario behavior checks.
- Targeted automated characterization/regression tests **and** preserved system-wide smoke tests; manual operator test over representative non-production state.
- SQL/DDL fingerprint unchanged and verified against reference; no migration runner/change to production DB.
- Every old entrypoint, callback, URL and Cron path required for compatibility continues to work, or an equivalent verified forwarding compatibility adapter exists.
- Exact-candidate independent review; compare code behavior plus database side effects and external requests, not only PHP syntax.
- Operator approves the validated increment before it becomes the base for the next; rollback remains viable.

## Security and publication constraints

Never place original SQL with customer/financial/integration data into a public repository. This public bootstrap intentionally omits actual rows, live runtime config, backups and logs. Search for additional embedded secrets before every push. Rotate any real credentials that were included in shared source/dump. Do not add deployment secrets to CI logs.

## Future naming

The official, case-sensitive product name is **AChBot** (not **AchBot**). Use this spelling in all new user-facing names, release titles, project docs, and source comments. Lowercase `achbot` remains an acceptable technical slug in paths, tests, release filenames and identifiers; do not rename working interfaces for spelling alone. Legacy `wizwiz` callback payloads and script paths are compatibility contracts, not just branding: replace them only with backward-compatible decoding/aliases, and do not break previously sent Telegram inline keyboards. Internal names can be simplified where not observable externally.

Previously approved, byte-frozen source excerpts and historical reference fixtures may retain earlier spelling. Branding changes never authorize changing runtime behavior, callbacks, Cron filenames, or database records.
