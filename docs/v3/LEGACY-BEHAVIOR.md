# Support behavior preserved, not silently repaired

These observations refer to the immutable V2 support code moved by V3. They are not new features, a full security audit, or authorization to exercise a real customer's ticket. No live-provider data or endpoints were used. Locations below are in `bot.php` at V2 commit `893032ef217fe89fa1d46b06a5c3368b8f4fb63e`; the module map in README identifies their new owner.

| Observation | Evidence | Treatment |
|---|---|---|
| Multi-digit rating ID is not captured as a whole | Original line 6937 uses a repeated single-digit capture. `rating.rate_123_5` asserts the SQL ID is `3`, not `123`; the whole-router case also reproduces it. | Preserve regex/data behavior now. A rating fix needs a separate explicit expected-ID test and accepted behavior change. |
| Customer closure changes shared actor state | Original line 6821 block assigns `from_id` from the ticket owner. Isolated cases compare the caller alias; the delegated-admin case observes both close paths running. | Do not localize the assignment or introduce first-match routing. This is a compatibility observation, not endorsement of the authorization policy. |
| Admin queue code changes shared admin context | Original queue and pagination blocks assign `admin` from each ticket's `user_id`; the last row can affect later checks and notifications. | Preserve scope and ordering; any role/context redesign needs complete dispatch evidence. |
| Customer pagination and admin pagination are not a single clean policy | Customer list emits `moreTicket_*`; the handler later has an admin gate. Admin pagination uses `5 + offset` as its count threshold. | Covered by denied customer pagination and native/isolated queue cases. Do not normalize silently. |
| Notifications can precede the message write | Creation/reply code binds `chats_info`, sends notifications, then executes the statement. Injected write/notification failures expose partial effects. | A transaction/outbox/retry policy is outside this extraction; preserve call order. |
| `setUser` does not refresh the request snapshot | Stored state changes while `userInfo` still reflects request-start data. Combined callback/wizard and source-swap cases exercise this. | Scoped dispatch must retain this distinction; native tests use the actual unchanged helper. |
| Category input has its own cancellation behavior | The `addTicketCategory` state condition lacks the usual cancel exclusion. Isolated `admin.category_cancel_legacy` preserves its write behavior; later root cancellation is a separate path. | Do not assume every wizard shares cancellation semantics. |
| Missing data and some queue rows produce warnings | Empty-record and undefined-value fixtures record matching warnings, including existing stale/undefined rate text. | Warnings are compared, not erased. No claim that legacy input handling is universally valid. |
| History can mutate `text` before the image-download condition | The history loop writes shared `text`; `history.cross_download` checks subsequent image selection in the isolated sequence. | Preserve fall-through. The full production reachability of every compound input is not claimed. |
| Image retrieval assigns an array to shared `text` | The attachment block changes `text` after JSON decoding. Later unrelated root conditions may not accept that type. | Isolated and native attachment outcomes are compared; do not claim the 32 whole-router cases cover every downstream attachment interaction. |
| Access checks vary between ticket operations | Selection/history/reply/close/category and image paths do not have a uniform ownership guard. | Original checks remain verbatim. A separate read-only security review should determine reachable impact before a scoped corrective change; no exploitation or production access is claimed here. |

Original V0-R01 through V0-R15 remain separately documented in the frozen V0 risk register. In particular, V0-R12's historical possible sensitive value is neither copied here nor declared fixed. Actual operator credential/invite rotation remains private work where applicable.

V3's new direct-script guard is limited to newly introduced files; it does not change existing bot.php permissions or historical callback behavior. Future domain/storage boundaries must distinguish compatibility quirks that remain required from bugs whose changed outcome the owner accepts.
